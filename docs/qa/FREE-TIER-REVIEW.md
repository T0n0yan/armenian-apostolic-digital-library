# Անվճար պլանի օպտիմալացում․ հաշվետվություն տիրոջ և Claude-ի համար

2026-10-28 · ճյուղ՝ `feat/free-tier-efficiency` · հիմք՝ `origin/main` / `a16267e`։
Տերը լիազորել է փոփոխությունները և production թողարկումը։ Ստորև «կատարված» նշանակում է կոդում իրականացված և տեղում ստուգված, ոչ ինքնաբերաբար production-ում աշխատող։

## Թողարկման վիճակ

Տեղական build-ը, typecheck-ը, lint-ը և 100 թեստից 99-ը անցել են։ Մեկ իրական Telegram թեստ բաց է թողնվել՝ համապատասխան մուտքի տվյալներ չկան։
GitHub API-ն, staging և production կայքերը այս միջավայրից վերադարձնում են proxy `CONNECT 403`։ Native Git ընթերցումն աշխատում է, GitHub-ի հանրային Actions էջն էլ հասանելի է։ Cloudflare-ի իրական հաշվի ընթերցման տվյալներ միջավայրում չկան։
Հետևաբար այստեղ **չի հաստատվում production-ի թողարկում կամ իրական օգտագործման թվերի ստացում**։ Git push-ի և staging-ի արդյունքը գրանցվում է `docs/work/integrations.md`-ում և հանձնման հաղորդագրությունում։

## Չափումներ և ստուգումներ

- Նույն մեքենայում, SQLite, մեկ թեմայում 2,000 սինթետիկ նյութ. նույն SQL արդյունքը՝ մինչև **0.83982 վրկ**, հետո **0.00527 վրկ**։ Մոտավոր SQLite VM քայլեր՝ **32,168,000 → 200,000**։ 500 նյութ՝ 2,042,000 → 50,000 քայլ։ Սա կոնկրետ հարցման լաբորատոր չափում է. VM քայլերը **D1 rows-read հաշվիչ չեն** և ամբողջ կայքի արագացման գործակից չեն։
- Chromium, 390×844, նույն տեղական fixture-ով գլխավոր էջի առաջին բացում. ռեսուրսների `transferSize` գումար՝ **1,535,973 → 1,286,378 byte**, մոտ **16.25%** պակաս։ Հեռացվել է 250,228 byte թռչնագրի անհարկի նախաբեռնումը։ Սա տեղական մատուցում է, ոչ production Brotli-ի կամ իրական հեռախոսի չափում։ LCP-ն այս փորձով էական չի փոխվել՝ մոտ 1.04 → 1.03 վրկ. LCP-ի մեծ արագացում չենք պնդում։
- 8 երթուղի բրաուզերով՝ գլխավոր, սաղմոսների բաժին, նյութ, որոնում, մեր մասին, կարգավորումներ, գաղտնիություն, սրբավայրեր։ 320/390/1440 լայնության ստուգումներում հորիզոնական overflow չկար, JavaScript page error չկար։ Առկա միջավայրում քարտեզի արտաքին tiles հարցումը արգելափակված է. քարտեզի աշխարհագրական տվյալների ամբողջական live ստուգում չի կատարվել։ Նախկին և նոր փորձերում navigation-ի ժամանակ presence հարցման ընդհատում արձանագրվել է. այցերի հավաքումը չենք փոխել։
- Սրբավայրի երկար էջ՝ MapLibre JS հարցում մինչև scroll՝ **0**, քարտեզին մոտենալուց հետո՝ **1**։ Reduced-motion-ի դեպքում մոմը հեռացված է, contextmenu-ն կանխարգելված չէ։
- `pnpm typecheck`, `pnpm lint`, `pnpm test`՝ անցած։ **100 թեստ, 99 անցած, 1 skip**։ Կան իրական Miniflare Worker/SSR/API ստուգումներ՝ մեդիայի range/seek, որոնում, պահված նյութեր, auth և abort-ներ։
- Նոր նպատակային ստուգումներ՝ հյուր/անդամ/սովորական ադմին/տեր մուտք, HTML և `.data` հասանելիություն, private/no-store, վահանակի մասնակի API ձախողումներ և չկարգավորված վիճակ, R2 snapshot, սրբավայրերի հրապարակային դաշտեր և sitemap, թաքցնելուց հետո որոնման քեշի անվավերացում, օգտագործվող մեդիայի բացառումը հաշվառումից, հիշեցումների TTL/հաշիվների մեկուսացում։
- Փոխված workflow YAML-ը կարդացվել է, shell հատվածներն անցել են `bash -n`։ **Սա GitHub/Cloudflare-ում backup կամ workflow live run-ի ապացույց չէ**։
- Speech գործիքը ստուգվել է 3 վրկ սինթետիկ WAV-ով՝ MP3 ստեղծվեց, երկրորդ գործարկումը վերօգտագործեց այն, բնօրինակը մնաց։ Քարոզի լսողական որակը դեռ պետք է համեմատել իրական նյութի վրա։
- Client bundle-ում `CF_ANALYTICS_TOKEN` և Cloudflare GraphQL endpoint չեն հայտնաբերվել։ Production տվյալներ չենք ներմուծել տեղական fixture-ի մեջ։

## Սուպեր ադմինի վահանակը

Հասցե՝ `/admin/usage`, հղումը՝ `/admin`-ում, միայն գլխավոր ադմինին։ Հաշվիչները ամբողջ **Cloudflare հաշվի** համար են՝ production, staging և նույն հաշվի մյուս նախագծերը միասին։

Հասանելի են՝ Workers requests, D1 rows read/write, D1 ընդհանուր պահեստ և ամենամեծ բազան, R2 պահեստ և Class A/B գործողություններ, Durable Objects invocations։ 80%-ից երևում է շեմին մոտենալու նշում, 100%-ից՝ գերազանցում։ Թվերը հարցվում են բացելիս կամ «Թարմացնել»-ով, հաջող/սխալ snapshot-ը պահվում է 60 վրկ տվյալ Worker օրինակում. համաշխարհային միասնական rate limit չէ։ Յուրաքանչյուր հարցում ունի 8 վրկ timeout, dataset-երի սխալները մեկուսացված են։ Չստացված թիվը **«Տվյալ չկա»** է։

Արտադրական Worker-ում պետք է ապահով կարգավորել՝

1. `CF_ANALYTICS_ACCOUNT_ID`՝ հենց Cloudflare հաշվի 32 նիշ ID-ն։
2. `CF_ANALYTICS_TOKEN`՝ այդ հաշվի Analytics ընթերցման համար նախատեսված առանձին, նվազագույն իրավունքներով token։ Այն մուտքագրել **Worker Settings → Variables and Secrets**-ում որպես գաղտնիք կամ Wrangler secret-ի անվտանգ prompt-ով, ոչ GitHub repo-ում, ոչ չաթում։ Թվերի dataset հասանելիությունը կախված է token-ի իրավունքներից և հաշվի պլանից. անհասանելի dataset-ը ցույց կտա բացակայող տվյալ։
3. Նույնը առանձին staging Worker-ի համար, եթե staging-ում էլ վահանակ է պետք։ Deploy-ի սովորական token-ը մի օգտագործեք էջի analytics-ի համար։

Տվյալները վերցվում են Cloudflare GraphQL-ից, ոչ սեփական «այցելու × միջին հարցում» հորինված հաշվարկով։ Այնուամենայնիվ սա հաշիվ-ապրանքագիր չէ՝

- Workers / DO analytics-ը կարող է նմուշառված լինել։ DO-ի WebSocket billing-ը տարբեր է invocations-ից։
- R2 պահեստը վերջին 24 ժամվա bucket-ների առավելագույն ծավալների գումարն է, ոչ ամսվա GB-month-ի ճշգրիտ գումարը։
- R2 Class A/B-ն ամսվա սկզբից հաշվարկված analytics է. անհայտ գործողության տեսակի դեպքում թիվը բաց է թողնվում։ Չվճարվող ձախողումները կարող են բարձրացնել թիվը, billing cycle-ը կարող է տարբերվել։
- Սահմանները Free/Standard պլանների հղման արժեքներ են. էջը վճարային պլանը չի որոշում։
- Workers CPU-ն և DO GB-s-ը չեն հաշվարկվում այս տարբերակում. կա Cloudflare dashboard-ի հղում։
- Օրական շեմերի UTC reset-ը Երևանի 04:00-ն է։

Աղբյուրներ՝ [Workers](https://developers.cloudflare.com/workers/platform/limits/), [D1](https://developers.cloudflare.com/d1/platform/pricing/), [D1 analytics](https://developers.cloudflare.com/d1/observability/metrics-analytics/), [R2 analytics](https://developers.cloudflare.com/r2/platform/metrics-analytics/), [R2 pricing](https://developers.cloudflare.com/r2/pricing/), [DO analytics](https://developers.cloudflare.com/durable-objects/observability/metrics-and-analytics/)։

## Կարգավորումից հետո միացվող հնարավորություններ

### Գաղտնագրված D1 backup

Workflow՝ `.github/workflows/private-backup.yml`։ Առանց երկու repository variable-ի այն բաց է թողնվում՝ գործող backup չձևացնելու համար։

- Ստեղծել առանձին **private** R2 bucket. `r2.dev` և custom public domains չպետք է միացված լինեն։
- Հուսալի տեղում ստեղծել `age` բանալիները։ GitHub variable `BACKUP_AGE_RECIPIENT`-ում դնել միայն հանրային recipient-ը։ Մասնավոր վերծանման բանալին պահել GitHub-ից և Cloudflare-ից առանձին ապահով վայրում։
- Repository variables՝ `BACKUP_R2_BUCKET`, առկա `CLOUDFLARE_ACCOUNT_ID`։ Secret՝ `CLOUDFLARE_BACKUP_TOKEN`, D1 export և միայն backup bucket upload-ի անհրաժեշտ իրավունքներով։
- Առաջին գործարկումը՝ ձեռքով։ Այնուհետև շաբաթական՝ կիրակի UTC 02:23։ Plain SQL-ը ջնջվում է կոդավորման ավարտից հետո, ժամանակավոր ֆայլերը մաքրվում են նաև սխալի դեպքում։
- Պահեստի չաճելու համար միայն այս առանձին bucket-ի `d1/` prefix-ի վրա սահմանել մոտ 30 օրվա retention՝ օրինակ Cloudflare Lifecycle Rule-ով։ Սա կջնջի հնացած backup-ները, ուստի ընտրել պահպանման ժամկետը տվյալների վերականգնման պահանջով։ Ընդհանուր մեդիայի bucket-ի վրա նման կանոն չկիրառել։
- Առաջին encrypted backup-ը ներբեռնել, վերծանել և վերականգնել **առանձին տեղական/փորձնական բազայում**։ Մինչև այդ «պահուստային պատճենը վերականգնելի է» չպնդել։ D1 backup-ը R2 մեդիայի առանձին պատճեն չէ։

### Խոսքի փոքր աուդիո տարբերակ

`node scripts/prepare-speech.mjs --speech INPUT OUTPUT_DIRECTORY`։ Գործիքը պետք է `ffmpeg`։ 64 kbps mono-ն 128 kbps ֆայլից տեսականորեն մոտ երկու անգամ փոքր կարող է լինել, բայց տարբերությունը կախված է բնօրինակից։ Սա **երաժշտության և շարականի ավտոմատ փոխարկիչ չէ**։
Բնօրինակը պահպանվում է։ Այս փոփոխությունը գոյություն ունեցող audio URL-ները չի փոխարինում, չի վերբեռնում R2 և բոլոր քարոզները ավտոմատ չի սեղմում։ Մինչև միացնելը՝ իրական քարոզի լսողական համեմատություն, checksum-ով վերբեռնում, D1 media metadata-ի migration/fallback և range/seek ստուգում։

## Աուդիտի մնացած կետերը՝ հստակ կարգավիճակով

1. **Ամբողջական static public shell / անձնական API բաժանում — չի իրականացվել**։ Կայքի ներկայիս SSR/auth/offline վարքը պահվել է։ Worker cache hit-ը դեռ հաշվում է Worker request. արդեն եղած R2/CDN մեդիան և static assets-ն ուրիշ ուղի են։ Այս փոփոխությունը 100,000 հարցման սահմանը չի վերացնում։
2. **Ավտոմատ R2 աղբահանություն — չի միացվել**։ Կա ընթերցող inventory, որն ընդգրկում է միայն 14 օրից հին, չհղված `v1/` գրադարանային օբյեկտների թեկնածուները։ Նկարներ, հրապարակումներ և պահուստային պատճեններ կույր ձևով չեն ջնջվում։ Delete-ի համար պետք է ամբողջական inventory, գործող sync-ի բացառում, grace period, backup և վերականգնման փորձ։
3. **Չհրապարակված սրբավայրերի մեդիայի առանձին private bucket — չի տեղափոխվել**։ Application route-ի auth-ը բավարար չէ, եթե նույն օբյեկտը հասանելի է հանրային R2 domain-ով։ Կոդի նախկին կառուցվածքում այդ ռիսկը կա. live հասանելիությունը ցանցային արգելքի պատճառով չի հաստատվել։ Պետք է private bucket, նոր upload/read binding-ներ, առկա draft ֆայլերի վերահսկվող տեղափոխում և CDN-ի հին URL-ների մաքրում։ Առանց իրական պահեստի և հղումների ստուգման տեղափոխելը կարող էր կոտրել նյութերը։
4. **WAF / արտաքին rate limiting — չի կարգավորվել**։ Cloudflare dashboard/API հասանելիություն չկա։ Ընթերցումների cache-ը և արդեն եղած query սահմանափակումները պահպանված են, բայց դրանք բոտային հարձակումից օրական quota-ի երաշխիք չեն։ Առաջարկ՝ փաստացի log-երով ընտրել հաճախ հարվածվող API-ները, աստիճանաբար սահմանափակել, բացառել Telegram webhook/auth callback և բնական ձայնային range հարցումները։
5. **DAU-ի նոր հաշվիչ — չի ավելացվել**։ Հին presence-ը սարքի մեկանգամյա այցելության նշում է, ոչ օրվա ակտիվ օգտատեր։ Այցելուների գաղտնիության և լրացուցիչ գրառումների ծախսը պահպանելու համար նոր heartbeat չկա։ Cloudflare requests-ը նույնպես մարդկանց թիվ չէ։
6. **Հանրային repo-ի պաշտպանություն — մասամբ ստուգված**։ Նախնական heuristic scan-ը դիտել է 371 commit / 1,847 եզակի blob և հայտնի token ձևանմուշներով արտահոսք չի գտել։ Դա երաշխիք չէ։ GitHub secret scanning/push protection և հին credential rotation-ի անհրաժեշտությունը պետք է ստուգել հաշվի կարգավորումներում։ Repo-ն հանրային դարձնելը չի նշանակում, որ ցանկացած runner/ծառայություն անսահման անվճար է։
7. **Live backup / analytics / speech rollout — կարգավորում են պահանջում**, ինչպես վերևում։ Այս աշխատանքի մեջ նոր վճարովի ծառայություն կամ պլան չի գնվել։

## Իրականում քանի՞ մարդու կարող է սպասարկել

Դեռ չափված պատասխան չունենք։ Առաջին մոտարկում՝ `(100,000 − ֆոնային հարցումներ − պահուստ) / մեկ օրական ակտիվ ընթերցողի Worker հարցումներ`։ Օրինակ 30,000 հարցում պահուստ թողնելու և 25 / 50 / 100 հարցում մեկ ընթերցողի դեպքում ստացվում է 2,800 / 1,400 / 700 ընթերցող։ Սրանք **օրինակային ենթադրություններ** են, ոչ կայքի չափված տարողությունը։ D1 read/write, CPU, DO և R2 սահմանները կարող են ավելի շուտ հասնել։

Փոփոխություններից հետո շահումը՝ ավելի քիչ ավելորդ բեռնում, շատ ավելի էժան title-index հարցում, փոքր public places projection, քիչ հիշեցման հարցումներ և օգտագործման տեսանելիություն՝ երբ միացվեն credentials-ը։ Իրական տարողությունն ապացուցելու համար պետք են 7–30 օրվա provider metrics և սովորական ընթերցողի session չափում, ոչ production-ի վրա կույր load test։

## Claude-ի համար՝ շարունակման քայլեր

1. Կարդալ այս փաստաթուղթը և `docs/work/integrations.md`-ի թողարկման վերջին նշումը։ `main`/`staging`-ի ուրիշ չաթերի commit-ները չվերագրել։ Տիրոջ production լիազորությունը արդեն տրված է։
2. Կիրառել cloud environment-ի պահպանված ցանցային կարգավորումները և նորից ստուգել GitHub API / staging / production հասանելիությունը։ Environment draft-ի պահպանումը չի կիրառում այն գործող մեքենայի վրա։
3. Staging-ում ստուգել որոնումը, նյութի աուդիո play/seek-ը, login/logout-ը, հիշեցումը, սրբավայրի թաքցնել/ցուցադրելը և owner-only վահանակը։ Եթե staging-ում ուրիշ չաթի փոփոխություն կա, PR-ը main մտցնել միայն այս feature branch-ից։
4. PR → main, հետևել Deploy-ի արդյունքին, հետո ստուգել production-ը։ Rollback՝ commit-ների սովորական revert/PR, ոչ force-push և ոչ բազայի reset։ Այս փաթեթը schema migration կամ production տվյալների ջնջում չի պարունակում։
5. Առանձին ապահով կարգավորել Analytics ընթերցումը և backup-ը, կատարել restore rehearsal։ Մնացած ենթակառուցվածքային կետերը վերևում հստակ բաց են մնացել։

Տեղական մանրամասն ապացույցները այս cloud workspace-ում՝ `/workspace/library-audit/after/`, թեստերի log-երը՝ `/tmp/efficiency-*.log`։ Դրանք production տվյալներ չեն և repo չեն ավելացվել։
